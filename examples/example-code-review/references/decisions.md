# 设计决策记录

> 记录本 Skill 在生成过程中的关键设计选择、放弃的方案、以及做出取舍的理由。
> 后续维护或升级时，先读本文件，避免推翻有充分依据的决定。

格式：每条决策包括 **决策 / 背景 / 备选 / 理由 / 影响**。

---

## D1：输出格式采用「问题 → 维度 → 建议 → 示例」四要素

**决策**：每条反馈固定包含位置、维度、问题描述、改进建议四要素，缺一不写。

**背景**：调研显示（参见 `research/02-common-issues.md`），AI 审查最常见的失败模式是"指出问题但不给方案"，让用户无从下手。

**备选方案**：
- A. 自由形式评论（更灵活）
- B. 严格四要素结构（本决策）
- C. 只输出 diff 形式的修改建议

**选择 B 的理由**：
- 强制结构能反"AI 倾向于啰嗦但无操作性"的失败模式
- 每条反馈可单独解析，方便用户筛选 / 工具化
- 与 Microsoft 审查清单（high-level + low-level）的格式契合
- C 方案太重，本 Skill 定位是"建议"而非"代写"

**影响**：所有维度的反馈必须能凝练成四要素；写不出建议的问题就不要提。

---

## D2：采用 4 级严重度（Critical / Major / Minor / Nit）

**决策**：使用 4 级而非 3 级或 5 级。

**背景**：业界主流是 3-5 级。Google 不强制分级，Microsoft 用 4 类标签，SonarQube 用 5 级。

**备选方案**：
- A. 3 级：Critical / Issue / Suggestion（简单但区分度低）
- B. 4 级：Critical / Major / Minor / Nit（本决策）
- C. 5 级：Blocker / Critical / Major / Minor / Info（精细但用户难记）

**选择 B 的理由**：
- 4 级正好对应"必须改 / 应该改 / 可以改 / 顺手改"四个层次
- Nit 单独成档，让"可改可不改"的小建议不污染主报告
- Major 与 Critical 的区分提供"阻塞合并"vs"非阻塞但重要"的边界
- 用户决策时只需问"低于哪个等级可以忽略"即可

**影响**：每条反馈必须明确分级；分级映射规则见 `assets/configs/severity-rules.yaml`。

---

## D3：不做自动修复，只给建议

**决策**：本 Skill 不输出可直接 apply 的 patch / diff，只在反馈中嵌入建议代码片段。

**背景**：是否提供 auto-fix 是当前 AI 审查工具最大的分歧点。CodeRabbit / Cursor 倾向自动改；Greptile / PR-Agent 偏保守。

**备选方案**：
- A. 输出完整 patch，用户一键 apply
- B. 输出 diff hunk，用户选择性 apply
- C. 仅在反馈中给代码片段示例（本决策）

**选择 C 的理由**：
1. **责任边界**：自动修复会让用户产生"AI 已经处理"的错觉，跳过自己的判断
2. **上下文不足**：Skill 看到的代码通常是片段，跨文件影响无法保证
3. **幻觉风险**：AI 在生成完整 patch 时编造 API 的概率显著高于只解释问题
4. **本 Skill 定位**：人工 + linter 之间的"第一双眼睛"，不是 fixer

**影响**：所有改进建议以代码 fence 形式给出，明确标注"示例"，不构成可执行 patch。

**未来可能反转**：当用户显式请求 `/review --fix` 时可考虑放开。当前不实现。

---

## D4：单次审查 ≤ 500 行的硬限制

**决策**：超过 500 行直接拒绝整体审查，要求用户拆分。

**背景**：SmartBear 研究表明审查速率超过 500 LOC/小时缺陷发现率显著下降；Google 建议 CL ≤ 400 行。

**备选方案**：
- A. 200 行（最严，与 Google 一致）
- B. 500 行（本决策）
- C. 不限制（依赖 AI 上下文窗口）

**选择 B 的理由**：
- AI 审查者不会"疲劳"，可比人工略放宽
- 500 行是大多数 PR 的合理上限，强制低于此值会让用户频繁拆分
- 超过 500 行的"审查"质量普遍不可信，宁可拒绝

**影响**：> 500 行触发拆分建议而非降级审查。

---

## D5：不确定的判断必须用问句而非断言

**决策**：当不能 100% 判定是否是 bug 时，输出形式为问句（"这里在 X 情况下会不会 Y？"），禁止使用断言。

**背景**：AI 幻觉是审查工具最致命的问题。一次错误的"自信断言"会让用户对整个 Skill 失去信任。

**备选方案**：
- A. 全部用断言，错了用户自己识别
- B. 加置信度分数（"我 70% 确定这是 bug"）
- C. 用问句缓和（本决策）

**选择 C 的理由**：
- 置信度分数本身也可能是幻觉，并未真正解决问题
- 问句天然引导用户"自己想一遍"，比给数字更有教育意义
- 与 Microsoft 的 `Question` 标签思路一致

**影响**：写入决策规则强约束。

---

## D6：默认跳过纯风格偏好问题

**决策**：缩进、括号位置、命名风格等纯偏好问题默认不输出，除非违反项目既定规范。

**背景**：调研显示风格争论占审查时间 15-20%，但产出 < 5% 真实价值。

**备选方案**：
- A. 全部输出，让用户决定
- B. 默认跳过，用户显式请求时输出（本决策）
- C. 永不输出

**选择 B 的理由**：
- A 等于鼓励 nit-picking
- C 太极端，项目有明确风格规范时确实需要查
- B 兼顾两类场景

**影响**：判断"是否风格偏好"需要主观判断，写入约束作为审查者的自我克制。

---

## D7：超过 15 条反馈强制截断

**决策**：单次报告反馈条目 > 15 时，只保留 Top 15，告知用户"还有 N 条次要建议可单独询问"。

**背景**：AI 倾向于"宁多勿少"，但 SmartBear 研究表明审查者一次专注容量约 60 分钟、约 500 LOC，对应反馈不应超过 15-20 条。

**备选方案**：
- A. 不限制条数
- B. 上限 10 条（更严）
- C. 上限 15 条（本决策）
- D. 按严重度浮动（Critical 不限，Minor/Nit 限）

**选择 C 的理由**：
- 15 是用户在一次注意力周期内能消化的合理上限
- D 看似精细但容易让 AI 把问题硬塞进 Critical
- 截断后给用户"还可以问"的出口，不算丢失信息

**影响**：写入约束。Critical 应该几乎不会触发上限；触发上限通常意味着代码本身需要重写而非审查。

---

## D8：不评价代码作者

**决策**：禁止任何对代码作者的评价用语（"写得不好"、"显然不懂 X"等）。

**背景**：人类审查的最大风险是攻击作者而非代码；AI 没有人际关系包袱，反而要更克制。

**备选方案**：
- A. 默认中性、个别情况允许"严厉"评价
- B. 全面禁止针对作者的评价（本决策）

**选择 B 的理由**：
- AI 没有团队语境，无法判断哪种语气合适
- 任何对作者的评价都对审查质量没增量

**影响**：约束写入护栏，硬规则。
